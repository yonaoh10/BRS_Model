# כמה זמן לוקח לעבד שיחה אחת

המספרים הבאים נמדדו על הקלטה אמיתית באורך **3:05 דקות** (185.6 שנ'), על
MacBook Pro עם **Intel i7‑9750H (6 ליבות) וללא כרטיס גרפי**, ועל GPU שכור
מסוג **RTX 4090** עבור השיפוט:

| שלב | זמן נמדד | הערה |
|---|---|---|
| קליטה (probe) | 0.1 שנ' | |
| המרת אודיו + VAD אנרגטי | ~2 שנ' | ברירת המחדל במצב mock |
| VAD של silero | 5.6 שנ' | 55 מקטעים, מקומי על CPU |
| **תמלול** (faster‑whisper, ivrit.ai large‑v3‑turbo, int8, CPU) | **172.7 שנ'** | beam 5 + VAD, ‏RTF ‏1.10x; טעינת מודל ~5–9 שנ' פעם אחת לתהליך |
| **הפרדת דוברים** (pyannote‑3.1, CPU, ‏num_speakers=2) | **228.5 שנ'** | ‏RTF ‏1.23x; ‏~221 שנ' מתוכן בשלב ה‑embeddings (‏19 קריאות). טעינת פייפליין 1.9 שנ' |

| טעינת פייפליין דיאריזציה community‑1 מקאש במצב offline | שניות בודדות | נבדק על השרת המרוחק; `HF_HUB_OFFLINE=1`, בלי טוקן |

### על ההקבלה של תמלול והפרדת דוברים

שני השלבים תלויים רק באודיו, ולכן הם רצים במקביל **בשני תהליכים נפרדים**
(הכרחי: ל‑ctranslate2 ול‑torch יש כל אחד libiomp5 משלו, ותהליך אחד שמחזיק
את שניהם קורס אקראית על מק אינטל). המדידה מראה שהתחרות על הליבות מאיטה את
שניהם — חלוקת ליבות מפורשת (3+3) דווקא הרעה (394 שנ') לעומת השארת ברירות
המחדל (~347 שנ') — ולכן הצינור לא כופה `OMP_NUM_THREADS`. הרווח נטו:
~55 שנ' לשיחת 3 דקות (13%). כיבוי: `speakers.parallel_diarization: false`.

## איך לקבל את המספר האמיתי שלכם

```bash
pip install faster-whisper
python scripts/download_models.py --asr
python scripts/benchmark_asr.py --audio data/input/calls/REAL001.wav
```

הסקריפט מדפיס כמה שניות אודיו מעובדות בכל שנייה של שעון (realtime factor),
כמה זמן לוקחת טעינת המודל — שמשולמת פעם אחת לתהליך ולא פעם אחת לשיחה — ותחזית
לאצווה. זו הסיבה ש‑`watch` מחזיק תהליך אחד פתוח במקום להריץ תהליך לכל קובץ.

## הערכות, עד שתמדדו

מה שעדיין **לא** נמדד אצלנו:

| | תמלול של שיחה בת 3 דקות | הפרדת דוברים | שיפוט LLM |
|---|---|---|---|
| CPU, 6 ליבות, int8 | **2:53 (נמדד)** | **3:49 (נמדד, pyannote‑3.1)** | לא מעשי |
| GPU (T4 / A10 / 4090) | 10–30 שניות (הערכה) | 3–10 שניות (הערכה) | **~7.5 דק' (נמדד, 27B על 4090)** |
| API חיצוני | — | — | 10–30 שניות (הערכה) |

הפרדת הדוברים רצה רק על הקלטה בערוץ אחד. בהקלטה עם שני ערוצים נפרדים העלות
שלה אפס, כי אין מה להסיק.

שיפוט על CPU אינו מעשי: מודל של 7–8 מיליארד פרמטרים מייצר על מעבד בודדים
בודדים של טוקנים בשנייה, וכרטיס ניקוד הוא כ‑2,500 טוקנים. זה עשר דקות ויותר
לשיחה, ובעברית האיכות תהיה גרועה ממילא — ועל תמליל אמיתי גם 7B על GPU לא עבר
את סף אימות הראיות.

## מה זה אומר בפועל

**התמלול והפרדת הדוברים רצים מקומית.** שיחה של 3 דקות מעובדת בכ‑6 דקות
(במקביל). לעשרות שיחות בלילה זה מספיק.

**השיפוט הוא מה שדורש GPU** — ולכן יש שתי דרכים לעקוף אותו בשלב הפיתוח:

1. **ענן ל‑GPU.** הקוד ב‑`cloud/` כבר עושה את זה, וניתן להסרה מלאה.
2. **API חיצוני.** מנוע השיפוט מדבר `POST /v1/chat/completions` עם
   `Authorization: Bearer` רגיל, כך שכל ספק תואם‑OpenAI מתאים: מגדירים
   `judge.base_url` ו‑`judge.api_key` ולא מרימים שום שרת. זו הדרך הזולה
   ביותר לשלב הפיתוח. **לא נבדק מול ספק אמיתי בשלב הזה** — צריך ריצה אחת
   כדי לאמת.

לשני המסלולים חל אותו כלל: **הקלטות של לקוחות אמיתיים לא יוצאות לענן ציבורי.**
שיחות מבוימות ומוקלטות בהסכמה — בסדר. בייצור, בשרתי הבנק, vLLM מקומי.

הערה תפעולית לענן: הכתובת הציבורית של RunPod ‏(proxy.runpod.net) עוברת דרך
Cloudflare, שמנתק כל בקשה שנמשכת יותר מ‑~100 שניות (שגיאת 524). שיפוט של
מודל 27B איטי מזה, ולכן העבודה מולו נעשית דרך מנהרת SSH אל הפוד, לא דרך
ה‑proxy.

## הערה על סביבת הפיתוח הנוכחית

מק אינטל: ל‑PyTorch אין גלגלי macOS x86_64 אחרי גרסה 2.2.2, ולכן pyannote 4
(‏community‑1) לא ניתן להתקנה מקומית לעולם. **הפרדת הדוברים המקומית בסביבה זו
רצה עם pyannote‑3.1, ששיעור השגיאה המדווח שלו על שיחות שני דוברים הוא בערך
כפול משל community‑1.** המספרים המקומיים שנמדדו כאן (228.5 שנ') הם של 3.1;
בשרת הלינוקס של הבנק חייבים לרוץ עם community‑1 — זו כבר ברירת המחדל
בקונפיגורציה (`speakers.diarization_model`), וטעינתו מקאש במצב offline
אומתה על השרת המרוחק.
